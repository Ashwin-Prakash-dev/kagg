# FAIR1M annotation validation and cleaning report

Generated by `scripts/validate_annotations.py`. Source of truth: `Dataset/labels.parquet` (read-only; never modified).

## 1. Coordinate convention (verified, not assumed)

`labels.parquet` carries both the FAIR1M oriented bounding box (OBB, four corners `x0,y0..x3,y3`) and a precomputed axis-aligned box (`x_min,y_min,x_max,y_max`). Checked over all 594,777 rows:

- The AABB equals the OBB corner extent **clipped** to `[0, ImageWidth] x [0, ImageHeight]` for **100.00%** of rows.
- It equals the *unclipped* extent for only ~99.6% of rows, i.e. clipping is genuinely applied and is the difference.

Consequence: the Part F checks for *negative coordinates* and *boxes outside image boundaries* return **0 on the stored AABB by construction**. Reporting only that number would be misleading, so both checks are also run against the underlying OBB, where the real out-of-raster geometry lives.

## 3. Investigation of the 406 'tiny boxes'

The dataset report's `tiny_boxes: 406` counts annotations with AABB area < 16 px^2. That figure conflates two completely different populations, which is why it had to be split before any cleaning decision:

- **297 are zero-area** (degenerate geometry).
- **109 are non-degenerate** 4-corner polygons that are simply very small.

### 3a. The zero-area boxes are source-annotation defects, not conversion errors

Counting *distinct* vertices in each source OBB separates the causes cleanly:

| Root cause | Count | Diagnosis |
|---|---:|---|
| `point_polygon` | 225 | All four OBB corners identical: source polygon collapsed to a single point, so the object has no extent in either axis. |
| `line_polygon` | 69 | OBB has only two distinct corners: a zero-area line segment, not a quadrilateral. |
| `sliver_polygon` | 2 | OBB has three distinct corners and collapses to zero width or height after clipping. |
| `outside_image` | 1 | Polygon lies entirely outside the image raster; clipping leaves no pixels. |

Three independent lines of evidence rule out a parsing or conversion error on our side, and point instead at the FAIR1M tiling pipeline:

1. The defect is present in the **source polygon itself** - e.g. `t_16385.jpg` Label_ID 896 stores `(-86,43)` four times over. There is no arithmetic that recovers an extent from a single repeated point, so nothing was lost in the AABB derivation.
2. **290 of the 297 unusable polygons (98%) sit on or beyond a tile boundary.** FAIR1M cuts a large scene into tiles; an object lying almost entirely outside a given tile still receives an annotation record in that tile, and its polygon collapses onto (or past) the edge. Only 7 degenerate polygons sit strictly inside a tile. A random labelling or parsing fault would not concentrate on the raster border like this.
3. The collapse is **clustered, not scattered**: 3 image(s) account for 120 of the 225 point polygons, and within each of those images every collapsed object shares one identical coordinate - consistent with a whole block of neighbouring-tile objects being projected to the same off-tile position.

Visual confirmation: `evidence/point_polygon__t_16385__905.png` shows the clipped location of a supposed *Small Car* falling on unbroken tree canopy - there is no vehicle there. `evidence/line_polygon__t_296__39282.png` shows a *Van* whose polygon `(336,0)-(345,0)` is a 9 px line lying exactly along the top tile edge: the vehicle itself is in the neighbouring tile.

## 6. Non-defects, explicitly

- **8,874 polygons cross a tile edge.** These are correct annotations of objects that genuinely straddle the tile boundary; FAIR1M tiles a larger scene. Their stored AABB is already correctly clipped to the raster, and they are kept.
- **Zero negative / out-of-bounds stored AABB coordinates.** Not because the check is trivially satisfied, but because clipping already happened upstream. Re-verified rather than assumed (section 1).
